# dsh-ee 第一版产品方案：从「功能齐全」到「让人想用」（2026-11-07）

> 这份文档回答三个问题：链路为什么别扭、要不要在 DSH 上做一个完整的企业工作台、技能与市场怎么串起来。最后给出开源第一版的定位、可持续维护的做法和路线。
>
> 依据：README、docs/ 下的设计文档、`demo_content.go` 里的示例内容、前端页面结构。我没有在真实 DSH 里逐页操作过，界面观感部分以你的判断为准。

---

## 0. 一句话诊断

**管理员这一侧已经做得很完整，员工这一侧却没有让人眼前一亮的时刻。**

服务端能做的事很多：RBAC、LDAP、额度、模型网关、npm 源、审核、连接网关、知识库、审计。但一个员工第一次打开 DSH，看到的只是一两个示例应用，不知道这东西能帮自己做什么。一个 IT 负责人在 GitHub 上看到这个项目，读完 README 记住的是「一个私有插件市场和 npm 源」，而不是「我们公司的 AI 工作台」。

所以问题不在功能缺了多少，在三个地方：

1. **信息架构是按开发者的心智组织的。** 插件、技能、提示词、连接、微应用、知识库是六种「资产类型」，这是搭建它的人怎么想；员工想的是「我要报销」「我要查客户」「我刚入职」。
2. **示例内容决定了第一印象。** 现在的示例只是「证明这个功能能跑」，还不足以「证明这个产品值得用」。
3. **各项能力之间没有闭环。** 每类资产各有一套创建、审核、下发的流程，但「建了知识库，然后呢？」「接了连接，然后呢？」「员工用得好不好，搭建的人知不知道？」这些都没有接上。

下面分别给出建议。

## 1. 先定一个产品主轴：「应用」是唯一的主角

### 1.1 两种身份，人人都能搭建

已定（2026-11-07）：**员工也能搭建应用。**「搭建」是一种行为，不是一个单独的角色。所以只分两种身份：

| 身份 | 他们关心什么 | 他们的主页 | 他们会看到的名词 |
|---|---|---|---|
| **员工**（全员） | 用：这东西能帮我办什么事<br>造：能不能把我自己的活做成应用，分享给同事 | DSH 里的「企业应用」启动台 + 网页「我的工作台」「我的应用」 | 用的时候只看到应用；造的时候才看到知识库、连接、技能、提示词 |
| **管理员**（IT / AI 负责人） | 安全、成本、有没有人用 | 网页「管理」 | 全部，再加模型、令牌、额度、审计、npm 源 |

现在员工和管理员看到的基本是同一套菜单，只是权限不同。建议**按「用 / 造 / 管」重新组织导航**，而不只是按权限把菜单项藏起来：

- **用**（默认首页）：企业应用、知识问答、我的工作台；
- **造**（一个「新建应用」按钮就能进去）：我的应用、从样板复制、原料（我能用的知识库、连接、技能、提示词）；
- **管**（只有管理员看得到）：现有的管理页面。

企业 AI 落地真正的瓶颈不在 IT 部门，而在于离业务最近的人愿不愿意、能不能把自己的流程沉淀下来。dsh-ee 已经有不用写代码就能配置工作台的能力，但现在它藏在「能力中心 → 微应用 → 编辑」里，看上去像一个管理功能。把它变成每个员工都能用的「新建应用」，是这次最重要的改变。

### 1.1a 员工搭建的三级：自己用 → 分享 → 全员

现状：成员角色默认就有「发布能力」权限（`registry.publish`），员工已经能提交技能、提示词和微应用，但每次提交都直接进入审核（除非收录模式是 open），没有「先做给自己用」这一步。所以门槛高、试错成本也高。

建议分三级：

| 级别 | 谁能用 | 要不要审核 | 怎么实现 |
|---|---|---|---|
| **自己用** | 只有自己 | 不用，保存就能在自己的 DSH 里打开 | 可用范围只有本人（`Scope.Users = [我]`）的应用跳过审核，下发方式固定为「自选」 |
| **分享给同事** | 指定的人、部门 | 要，走现有审核队列 | 现有流程 |
| **全员默认启用** | 范围内所有人 | 要，而且只有管理员能设 | 现有流程（「自动生效」需要管理权限） |

让「自己用」免审核是安全的，原因是**应用本身不带权限**：员工只能选自己已经有权限的知识库、连接工具和技能，应用运行时也是以员工本人的身份调用，经过同一个连接网关、同一套工具级授权和审批卡。员工自建的应用做不到他本人做不到的事。新建企业连接、配置凭据仍然只有管理员能做。

做法上，「自己用」还是那个应用，只是范围窄。想分享时改一下范围，就会自动进入审核，不用重新创建。

### 1.2 重新定义名词关系

```
                 ┌──────────────── 应用（员工唯一需要理解的东西）────────────────┐
                 │  人设 + 工作台面板 + 示例问题                                │
                 │        │          │          │          │                   │
                 │     知识库      连接       技能       提示词                  │
                 │   （读什么）  （办什么）  （怎么做）  （常用说法）              │
                 └────────────────────────────────────────────────────────────┘
       插件 = 给技术人员的扩展机制（大多数员工不需要看到）
```

- 对员工来说，**能力中心改成「应用」**：只展示应用。技能和提示词如果是「默认启用」的，员工根本不需要知道它们的存在；如果是「自选」的，就放在应用详情里，或者放进一个次级的「更多工具」Tab。
- **插件从员工视角里拿掉**，只在「造」的高级选项和管理员视角里出现。npm 源、插件审核这些仍然很有价值，但它们是治理能力，不是产品卖点。
- 员工在「造」的时候，知识库、连接、技能、提示词是「原料」，应用是「成品」。每一种原料的页面上都要能直接回答：**这份原料被哪些应用用了？还能拿它做什么应用？**

## 2. 示例应用：从「一个演示」到「一个样板间」

### 2.1 为什么这一点最要紧

开源项目的第一印象，八成来自 `docker compose up` 之后的头十分钟。这十分钟里，用户看到的只能是示例内容。**示例应用就是产品本身。** Notion 的模板库、Retool 的示例应用、Dify 的应用模板，都是这个逻辑。

### 2.2 虚构一家完整的示例公司

不要做零散的示例，要虚构一家公司，比如「星河科技」，200 人，有研发、销售、财务、HR、IT 几个部门。一键导入后得到：

- 组织架构和 8～10 个角色各不相同的演示员工（已经有 6 个，补上部门负责人；其中一两个员工预置了自己搭建的「自己用」应用，演示人人都能搭建）；
- 每个部门 1～2 个知识库，文档写得像真的一样（制度、手册、FAQ、产品资料）；
- 3～4 个**内置演示业务系统**，沿用 `/demo/travel/*` 的做法：差旅报销、CRM、工单、HR 假期，数据有几十到几百行，带有趋势和异常值，看起来才像真实数据；
- 8 个精心打磨的应用（见下表）；
- 一段近 30 天的模拟使用数据，让管理总览、运营数据页一打开就有曲线，而不是空白。

### 2.3 第一版建议的 8 个样板应用

挑选原则：覆盖不同部门；每个应用都用到不同的能力组合；每个应用都有一个 30 秒内就能看到效果的「哇」时刻。

| 应用 | 部门 | 用到的能力 | 30 秒「哇」时刻 | 工作台面板 |
|---|---|---|---|---|
| 出差报销助手（已有，重做） | 财务 | 知识库 + 读写连接 + 审批卡 | 填三项信息，AI 按制度逐条算出可报金额并标出处，确认后直接提交 | 本月已报 / 待审指标，报销单表格，计算结果看板 |
| 新人入职助手（已有，重做） | HR | 知识库 | 「我第一周要做什么」→ 生成带勾选框的个人入职清单 | 入职进度清单，常问问题，联系人卡片 |
| 客户拜访简报 | 销售 | CRM 连接 + 知识库（产品资料） | 输入客户名，一页简报：合同、近期工单、续约风险、推荐话术 | 我的客户表格（行按钮「生成简报」），到期提醒 |
| IT 服务台 | IT | 知识库 + 工单连接（写） | 「VPN 连不上」→ 先按手册排障，解决不了再自动建工单，单号写回面板 | 我的工单，常见故障一键自助 |
| 合同初审 | 法务 | 技能（审查要点）+ 知识库（标准条款） | 上传合同，按条列出风险和对应的标准条款 | 风险清单看板，条款对照 |
| 经营数据问答 | 管理层 | 只读数据连接 + 指标口径知识库 | 「上月华东 GMV 为什么下降」→ 拆解，配图表，并说明口径 | 核心指标，AI 生成的图表 |
| 周报助手 | 全员 | 提示词 + 工单 / Git 连接（只读） | 自动拉取我本周的工单和提交，生成周报初稿 | 本周素材清单，周报草稿 |
| 企业知识问答（已有 kb-qa） | 全员 | 全部知识库 | 跨库提问，带出处 | 已有 |

考虑到只有一个人维护，建议分两批：**第一批 4 个**（出差报销、新人入职、IT 服务台、客户拜访简报），已经覆盖知识库、读写连接、审批卡和工作台的全部组件；其余 4 个放到 v1.0 之后，也可以作为第一批社区模板投稿的范例。

样板应用要覆盖 dsh-ee 的全部核心能力，**它同时也是功能演示和教学材料**。员工想做自己的应用时，打开一个最接近的样板，点「复制为我的应用」改一改就行。

### 2.4 每个样板应用的质量标准

上线前每个应用都按这张表过一遍：

- [ ] 有图标、一句话说明，以及「它能帮你做什么」的三个要点
- [ ] 有 3～5 个示例问题，点一下就能跑，而且每一个都确实能跑通（写进 e2e）
- [ ] 工作台首屏不需要 AI 参与就有内容（指标、表格），而不是一片「暂无数据」
- [ ] 至少一个组件能让 AI 把结果写回面板（看板）
- [ ] 有出处（知识库）或有审批（写操作），体现「可信」这个卖点
- [ ] 空状态、加载中、无权限、出错四种状态都设计过
- [ ] 在真实 DSH（Desktop + Mac）上截过图，截图可以直接用在 README

### 2.5 工作台组件需要补的能力

现在的六种组件（指标、表格、表单、快捷按钮、说明、AI 看板）够用了，但要做出好看的样板，建议补这几样（按优先级）：

1. **图表**（折线、柱状、饼图）：数据问答、经营类应用离不开。数据源和指标卡相同，都是只读工具。
2. **清单 / 进度**：入职、项目交付这类场景，可以勾选，状态保存在会话里。
3. **详情卡**：表格里点一行，展开这条记录的字段，也就是「客户卡片」「工单卡片」。
4. **视觉细节**：骨架屏、空状态插画、数字变化动画、组件之间的间距和分组标题。这些花不了多少工夫，却直接决定「好不好看」。

坚持原有原则：面板上的按钮不直接改数据，只发话给 AI。这是安全卖点，也是区别于传统低代码工具的地方。

> 2026-11-07 补充：应用可以自带小表以后，建议把这条修正为「直接写只限应用自带的表；企业系统的写操作仍只走 AI + 审批卡」（已定，见 §10.3、§10.9）。

## 3. 要不要在 DSH 上做一个「完整的企业工作台」？

### 3.1 结论：要做，但不要做成「门户」，要做成「启动台 + 我的待办」

**不建议**做一个大而全、包罗一切的企业门户页面。原因有三：

1. 企业已经有 OA、飞书、钉钉、企业微信，再做一个门户只会和它们竞争，而且必输。
2. DSH 的核心交互是对话。一个巨大的仪表盘页面会和对话抢主角，看起来像「另一个后台」。
3. 技术上，DSH 没有给插件留整页的位置。像 dsh-worktable 那样画浮层、改页面结构，你之前已经判断过这条路太脆弱（见 `docs/workbench-panels.md`）。

**建议做的**是一个分两层的「企业首页」。它回答员工打开 DSH 时的两个问题：**我能用 AI 做什么？有什么事在等我处理？**

### 3.2 第一层：新对话首屏的「企业应用启动台」

位置：`conversation.hero.options`（list slot，插件可以放卡片），也就是员工每次新建对话都会看到的地方。

```
            ┌────────────────────────────────────────────────┐
            │  星河科技 · 早上好，张伟                         │
            │                                                │
            │  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐            │
            │  │🧾 报销│ │👥 客户│ │🛠 IT  │ │📚 问答│  全部应用 → │
            │  └──────┘ └──────┘ └──────┘ └──────┘            │
            │                                                │
            │  试试问：                                        │
            │  · 我上周去上海出差，住宿能报多少？                  │
            │  · 华东区下月到期的客户有哪些？                     │
            │                                                │
            │  需要你处理：2 张报销单待补票据 · 1 个工单待确认       │
            └────────────────────────────────────────────────┘
                         [ 输入框 ]
```

- 应用卡片按「我常用 → 部门推荐 → 全公司热门」排序；
- 示例问题从各个应用的示例问题里轮换挑选；
- 「需要你处理」这一行来自各应用贡献的待办（见 3.4）。

这块面积不大，却是**每天都会看到的地方**，价值远高于一个需要专门打开的大页面。

### 3.3 第二层：「企业工作台」系统应用

做法和 `kb-qa` 一样，用代码生成一个系统微应用，名字就叫「工作台」。打开后，右侧栏的面板是员工的个人仪表盘：

- 我的待办（汇总各应用）
- 我的应用（可以拖动排序、固定）
- 本月 AI 用量与额度
- 公司公告 / 新上线的应用
- 最近的会话（按应用分组）

左边对话区就是一个「总助理」：知道员工能用哪些应用，可以把员工转到对应的应用里去（「这个问题用报销助手处理更合适，要打开吗？」）。

好处是**完全复用现有机制**：右侧栏、面板组件、会话绑定都是现成的，不需要新的技术冒险。

### 3.4 关键设计：应用向首页贡献「小组件」

把首页和各个应用连起来的方式，是**每个应用都可以声明 0～2 个「首页卡片」**，类似手机的桌面小组件：

- 报销助手贡献「待补票据 2 张」；
- IT 服务台贡献「工单处理中 1 个」；
- 客户简报贡献「本周拜访 3 家」。

数据源仍然是只读连接工具，配置方式和工作台组件相同，应用作者在编辑器里多勾选一项「显示在首页」即可。这样首页不需要单独维护内容，**应用越多，首页越有用**，这是一个自然生长的结构。

### 3.5 网页端「我的工作台」怎么办

网页端的 `/workbench` 现在侧重令牌、用量、装过的能力，偏「账户中心」。建议：

- 和 DSH 里的「工作台」用**同一份数据**（我的应用、待办、用量），保持一致；
- 网页端额外提供 DSH 里不方便做的事：应用的完整详情与说明、申请权限、查看我的历史；
- 「我的微应用」的模拟数据要换成真实数据（README 里标注过这一项）。
- 2026-11-07 补充：应用本身也能发布成网页版（`/a/<应用标识>`，和 DSH 共用一套渲染，手机可用），见 §10.4。

## 4. 把能力中心串成一个闭环

### 4.1 现在缺的环节

一个能力完整的生命周期应该是这样的：

```
  ① 原料           ② 组装          ③ 发布          ④ 发现          ⑤ 使用          ⑥ 反馈
 知识库/连接  →   做成应用   →   审核+授权   →   员工看到   →   在 DSH 用   →   好不好用
     ↑                                                                         │
     └──────────────── ⑦ 改进 / 员工把好用的对话沉淀成新能力 ←────────────────────┘
```

现在 ①③⑤ 做得很扎实，②④⑥⑦ 比较薄，所以感觉「联动不好」。

### 4.2 具体建议

**② 组装：每种原料都指向「做成应用」**

- 建好知识库后，页面直接给出「用这个库生成问答应用」，一键生成一个带示例问题的应用草稿（模型可以读文档，自动拟出示例问题）。
- 接入连接后，给出「用这个连接做应用」，按工具清单自动建议面板：只读的列表工具对应表格，返回数字的工具对应指标卡，写工具对应快捷按钮。
- 应用编辑器从「填表单」升级成「**左边配置、右边实时预览工作台**」。作者看得到效果，才愿意继续打磨。

**④ 发现：员工能看懂、能申请**

- 应用详情页列出它依赖的原料，并标出员工当前的状态：「✅ 可用」「🔒 需要 CRM 只读权限：申请」。点申请就进入统一的审批流，审批人收到通知。
- 统一「申请 → 审批」：现在审核队列是按资产类型分的，对员工来说应该只有一个「我的申请」。
- 新上线的应用在 DSH 首屏（3.2）出现一个「新」标记。

**⑥ 反馈：让应用作者知道应用好不好用**

这是现在最缺的一环，也是让作者持续投入的关键：

- 每次回答下面加 👍👎（DSH 支持的话做在插件里，不支持就做在看板上）；
- 应用详情给作者看：运行次数、使用人数、好评率、**答不上来的问题**（知识库检索为空、工具报错、用户点了 👎）；
- 「答不上来的问题」直接列成待办：「有 12 个人问过『年假能不能跨年』，知识库里没有答案，要补一篇文档吗？」

**⑦ 沉淀：从对话到能力**

这是产品的飞轮，也是开源宣传里最有说服力的一点：

- DSH 里加一个命令 `/ee-save`：把当前这段好用的对话**沉淀成提示词、技能或者应用草稿**，带上原始对话作为说明，提交到 dsh-ee；
- 先存成「自己用」的能力（免审核，§1.1a），想分享时再走审核，通过后按范围下发；
- 员工工作台显示「我分享的能力被 37 人用了 210 次」。

这样就把 landing 页上「员工沉淀的新 Skill 回到企业作用域，供全员复用」这句话真正落了地。

## 5. 开源第一版：定位与首次体验

### 5.1 定位

**一句话：** dsh-ee 是给 DeepSeek Harness（DSH）用的开源企业版，让企业把自己的知识和业务系统做成 AI 应用，安全地发给每一位员工。

> 2026-11-07 补充：有了应用自带数据和网页版（§10）以后，可以考虑换成更直观的说法：「**人人都能做的企业小系统：DSH 里有 AI 帮你做，网页上谁都能用。**」待定。

**三个关键词**（README 首屏、落地页、宣传材料都只讲这三个）：

| 关键词 | 对谁讲 | 证据 |
|---|---|---|
| **业务应用，不止对话** | 员工、业务部门 | 每个应用都有自己的工作台面板；8 个样板应用 |
| **一次接入，全员可用** | IT 负责人 | 一行命令 / 一段提示词接入；授权后自动下发，不用逐台安装 |
| **私有、可审计、可控成本** | 安全与管理层 | 私有部署、离线安装、凭据不落员工电脑、写操作审批、按人额度、审计日志 |

插件市场、npm 源、模型网关、RBAC、LDAP 这些作为「完整的企业级底座」放在第二屏，作用是消除顾虑，而不是吸引注意。

### 5.2 目标用户

第一版先服务好一类人：**200～5000 人企业里负责推广 AI 的 IT / 数字化负责人**，公司已经决定（或正在评估）在内部用 DSH。

- 他的 KPI 是「全员用起来」和「不出安全事故」；
- 他需要拿给老板看的东西：使用率、节省的工时、哪些部门在用；
- 他担心的事：员工乱装插件、数据外泄、费用失控。

管理总览和运营数据页正对应这些需求，建议加一个「**月度 AI 落地报告**」，一键导出 PDF：活跃率、各应用使用量、热门问题、估算节省的工时。这是 IT 负责人向上汇报时最想要的东西，也是很好的口碑传播点。

### 5.3 首次体验：十分钟原则

一个陌生人从看到 README 到「哇，这个好用」，要控制在十分钟以内：

## 6. 只做开源：怎么让一个人维护得下去

dsh-ee 只有开源版，全部功能都开源，不规划商业版，目前是个人用爱发电。所以本节不谈收费，谈的是**在有限的业余时间里，怎么让项目既受欢迎又不把维护者拖垮**。

### 6.1 原则

1. **功能不分版本。** 现有的一切（含 LDAP、审计、额度、离线安装）都开源，以后加的 OIDC、飞书 / 钉钉集成也一样。企业愿意用，口碑自然来。
2. **少做比多做重要。** 每加一个功能，就多一份要长期兼容上游 DSH 的负担。第一版的「不做」清单（§7）要守住。
3. **能自动的都自动。** 维护者最大的时间消耗是「上游升级后哪里坏了」和「用户环境不一样」。e2e 场景、兼容性矩阵、一键诊断（`/ee-status`、设置页的连通测试）就是为了少回答重复的 issue。
4. **把能交给社区的交出去。** 见 6.3。

### 6.2 许可证

建议 **Apache-2.0**：企业法务最熟悉、最容易批准内部使用，对「被企业采用」这个目标阻力最小。AGPL 能防止别人闭源托管，但很多企业的合规流程会直接拒绝 AGPL，和这个项目的目标冲突。

### 6.3 社区能参与的地方（按门槛从低到高）

| 参与方式 | 门槛 | 对项目的价值 |
|---|---|---|
| 在 Discussions 的「谁在用」帖里留言 | 最低 | 代替遥测，知道有哪些企业在用、用在什么场景 |
| 报告某个 DSH 版本 / 系统上能不能跑 | 低 | 补全兼容性矩阵，维护者不用每个环境都测 |
| 投稿应用模板（应用定义 + 示例知识文档） | 中，不用写代码 | 样板应用越来越多，覆盖维护者想不到的行业 |
| 翻译 | 中 | 已有 i18n 结构，英文社区可以自己补 |
| 写连接器（某个常见系统的 OpenAPI 描述 / MCP 配置） | 中 | 降低其他企业接入同类系统的成本 |
| 代码 PR | 高 | 在 issue 上标好 `good first issue` |

### 6.4 衡量成功

不加遥测：对个人项目来说，遥测既增加维护量，又会让企业用户顾虑。用公开信号就够了：

- 「谁在用」帖里的企业数量和场景
- 是否有非样板的应用模板投稿（说明有人真的在搭建）
- issue 里「装不上 / 连不上」类问题的占比（这个比例下降，说明首次体验变好了）
- Star 和 fork 只作参考

### 6.5 控制维护者自己的成本

- **不做在线 Demo。** 它要服务器和模型费用，公开环境还要防滥用。用户在自己电脑上部署后一键导入示例公司就能体验，效果更真实；README 动图和演示视频负责「先看看」。
- **路线图不承诺日期**，只承诺顺序。
- issue 模板强制填写 dsh-ee 版本、DSH 版本、Desktop / CLI / Web、系统，以及 `/ee-status` 的输出，减少来回追问。

## 7. 路线

> 只承诺顺序，不承诺日期，按业余时间推进。已定：**先把全部功能做完，再发布**，演示视频最后录。逐项任务和完成标准见 [product-v1-tasks.md](./product-v1-tasks.md)。

1. **内容与组件**（M1～M3）：示例公司「星河科技」与一键导入 / 清除、工作台组件升级、第一批 4 个样板应用
2. **人人都能搭建**（M4、M5）：「用 / 造 / 管」导航、「自己用」免审核、从样板复制、实时预览、原料一键生成应用、应用导入导出
3. **串起来**（M6～M9）：DSH 首屏启动台与「工作台」系统应用、依赖与一键申请、👍👎 与答不上来的问题、`/ee-save`
4. **收尾功能**（M10）：OIDC、月度 AI 落地报告
5. **数据与网页**（M12～M15，§10）：从 DSH 打开网页免登录、应用自带数据、网页版应用、数据中台最小版本
6. **发布 v1.0**（M11）：README、文档、兼容性矩阵、模板仓库、演示视频；发布渠道是 GitHub、DSH 社区、V2EX、掘金、少数派，以及 AI 落地相关的公众号，文章写「我们怎么让 200 人的公司一周内用起 AI」这样的故事，而不是功能列表
7. **之后按社区需求推进**：数据升格、`data__query` 探索式分析（若未进 v1.0）、其余 4 个样板应用、飞书 / 钉钉 / 企业微信登录与通知、SCIM 同步组织架构、行业模板，欢迎社区认领

### 第一版明确不做

范围收住才能做精，下面这些先不做：

- 不做独立的整页门户，不画浮层（理由见 §3.1）
- 不做向量检索（现有的 Agent 检索方案就是差异化）
- 不做通用工作流编排 / 定时任务（会把产品带向 Dify / n8n 的赛道）
- 不自己重新打包 DSH Desktop（已定：同步官方包）
- 不新增资产类型：先让现有六种用起来（应用自带的表属于应用，数据中台挂成系统连接 `data`，都不算新类型）
- 中台不做定时同步 / ETL，不做行级权限；dsh-ee 不做身份提供方（IdP）；网页版应用不做匿名公开链接（§10）

## 8. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 上游 DSH 还在 rc 阶段，插件接口经常变化 | 每次升级都可能出问题，社区 issue 激增 | 兼容性矩阵；e2e 场景覆盖每个支持的版本；接入插件做好降级（例如首屏 slot 不存在时退回侧栏入口） |

| 商标 | 名称、宣传被要求修改 | 严格遵守上游品牌规范 |
| 功能广度大于打磨深度 | 每样都有，每样都不够好 | 坚持第一版「不做」清单；按 M1～M11 的顺序推进，不临时插入新的资产类型 |
| 维护者精力有限 | 更新变慢、issue 积压，项目看起来像没人管 | 守住「不做」清单；路线图不承诺日期；issue 模板和自助诊断减少来回追问；把模板、连接器、翻译交给社区（§6.3） |
| 应用自带数据后变成「数据系统」 | 用户把它当数据库用，出现数据量、备份、丢数据的问题 | 每个应用的行数上限、CSV 导出、删除后保留 30 天、写入审计；数据多了引导升格进中台（§10.3、§10.5） |
| 网页版扩大了暴露面 | 不装 DSH 的人也能访问，权限出错影响更大 | 必须登录、范围和应用一致、取数走同一个网关；一次性登录链接不带管理权限（§10.4、§10.6） |
| 样板应用依赖模型能力 | 演示时模型没按格式输出，效果翻车 | 示例问题写进 e2e，用真实模型定期跑；提示词针对 DeepSeek 调优 |

## 10. 补充：应用自带数据、网页版应用、数据中台与单点登录（2026-11-07 讨论）

> 起因：本地试用 M1 / M2 后的三个想法：① 在「连接」里做一个小数据中台，让企业数据真正用起来；② 从 DSH 打开知识库原文等网页时还要再登录一次；③ 工作台里的应用能不能也放到网页上用。进一步的设想是：员工在 DSH 里做的小应用可以有**自己的小数据库**，在 DSH 里用 AI 操作，也能发布成网页上的独立小应用；以后需要时，再接中台里的**唯一数据源**。
>
> 结论：方向成立，而且和现有架构很顺。这一节把它落成设计，任务拆在 [product-v1-tasks.md](./product-v1-tasks.md) 的 M12～M15。

### 10.1 应用的新定义：每个应用都是一个「带 AI 的小系统」

现在的应用 = 人设 + 工作台 + 原料（知识库、连接、技能、提示词），数据全部来自外部。补上「自带数据」和「网页版」以后：

```
                        ┌──────────── 一个应用 ────────────┐
                        │  人设 + 工作台配置（同一份 JSON）  │
                        │                                  │
   在 DSH 里用 ────────→ │  AI 对话 + 工作台：能读、能问、    │
   （有 AI）             │  能让 AI 改数据、能走审批卡        │
                        │                                  │
   在网页上用 ─────────→ │  同一个工作台：能看、能填表、      │
   （没有 AI，手机也行）  │  能改自带的数据；要 AI 时「去 DSH 继续」│
                        │                                  │
                        │  数据：① 自带的小表                │
                        │        ② 中台的数据集（唯一数据源） │
                        │        ③ 企业系统（连接）          │
                        └──────────────────────────────────┘
```

对员工来说，这件事的意义是：**一个人花十分钟，就能做出一个真的能用的小系统**，比如团建报名、设备借用登记、客户跟进台账、面试反馈收集。以前这类需求要么用共享表格凑合，要么排队等 IT 开发。dsh-ee 的差别在于：它天然带企业身份和权限，DSH 里有 AI 帮你填和查，网页上谁都能打开。

它没有新增资产类型（§7「不做」清单）：数据表是应用的一部分，中台是一个系统连接，跟知识库挂成 `kb` 是同一个做法。

### 10.2 三层数据，各管一件事

| 层 | 是什么 | 谁来建 | 存在哪里 | 典型内容 |
|---|---|---|---|---|
| **① 应用自带数据** | 应用里声明的几张小表 | 应用作者（任何员工） | dsh-ee 自己的库 | 报名记录、借用登记、跟进备注、反馈 |
| **② 中台数据集** | 企业共用的、一份说了算的数据 | 管理员（或审批后的员工升格，见 10.5） | 单独的 `dsh_ee_data` 库 | 客户主数据、组织与人员、产品目录、上传的经营报表 |
| **③ 企业系统** | 已有业务系统的接口 | 管理员配置连接 | 企业自己的系统 | CRM、工单、差旅、ERP 的实时数据和写操作 |

**唯一数据源原则**：主数据（客户、人员、产品）只存在 ② 或 ③ 里。应用自带的表只存「这个应用自己产生的数据」，要关联主数据时**存编号、不存副本**。比如跟进台账里存 `customer_id`，显示时再去中台取客户名称。这样一个客户改了名字，所有应用里看到的都一致，也不会出现十个应用各存一份客户表的情况。编辑器在作者想建一张「客户表」时，可以提示：「中台里已经有客户主数据，要不要直接引用？」

### 10.3 应用自带数据怎么设计

**声明方式**：在应用定义里加 `tables`，和 `workbench` 并列：

```json
"tables": [{
  "name": "signups", "title": "报名记录", "visibility": "own",
  "fields": [
    { "name": "name", "title": "姓名", "kind": "user" },
    { "name": "session", "title": "场次", "kind": "select", "options": ["周六上午", "周六下午"] },
    { "name": "diet", "title": "忌口", "kind": "text" },
    { "name": "customer_id", "title": "客户", "kind": "ref", "ref": { "dataset": "customers" } }
  ]
}]
```

字段类型先只支持 text、number、money、date、select、bool、user（自动填当前员工）、ref（引用中台数据集的编号）。

**谁能看到哪些行**（`visibility`，三选一，覆盖绝大多数场景）：

| 模式 | 行为 | 例子 |
|---|---|---|
| `own` 各自填写 | 每人只看到、只能改自己的行；作者和应用管理员看全部 | 报名、请假登记、问卷 |
| `shared` 共同维护 | 能用这个应用的人都能看、都能改 | 团队台账、设备借用 |
| `author` 作者发布 | 只有作者和应用管理员能写，其他人只读 | 值班表、公告、价目表 |

**存储**：所有应用的行存在 dsh-ee 库里的同一张通用表，形如 `app_rows(app_id, tbl, row_id, data JSON, owner_id, created_at, updated_at, deleted_at)`。不为每个应用建真实表。好处是不跑建表语句，作者改字段不用迁移，权限和审计也只需要在一处做。代价是不适合大数据量，所以加上限：每个应用默认最多 1 万行、单行最多 16 KB，管理员可以调。超过上限说明这份数据该升格进中台了（10.5）。

**改字段的规则**：可以加字段、改标题、加选项；删字段只是隐藏，数据保留；改类型只允许放宽（比如 number 改成 text）。这样作者怎么改都不会丢数据。

**AI 怎么操作**：系统连接 `app` 提供 `app__rows`（查询，可筛选和排序）、`app__insert`、`app__update`、`app__delete`，作用范围是员工当前能用的应用，行级可见性在服务端执行。规则如下：
- 新增、修改自己的行：直接执行，并写审计；
- 删除，或一次改 / 删超过 N 行：走现有的审批卡；
- 工作台的 `source` 可以写简写 `{"table": "signups"}`，表单的 `submit` 可以写 `{"table": "signups"}`，提交后直接插入一行。

**对现有原则的修正**（已定，见 10.9）：§2.5 说「面板上的按钮不直接改数据，只发话给 AI」。建议改成：**直接写只限于应用自带的表；企业系统（连接）的写操作，仍然只能经过 AI + 审批卡。** 应用自带的表本质上就是一张有权限的电子表格，填一张报名表还要过 AI，体验会很别扭；而企业系统才是需要安全卖点的地方。

**数据的安全网**：
- 每张表都能导出 CSV（作者和应用管理员可以导出）；
- 删除应用时，数据保留 30 天，可以恢复；
- 每次写入都记审计（谁、哪张表、哪一行、改前改后）；
- 「自己用」的应用照旧免审核；改成分享以后，表结构跟着应用一起进审核，审核页显示「这个应用会收集哪些字段」。

### 10.4 网页版应用

**入口**：应用编辑器里有一个开关「在网页上也能用」，地址是 `/a/<应用标识>`。能打开的人就是能用这个应用的人（和应用的范围一致），必须登录，第一版不做匿名的公开链接。

**渲染**：和 M5 的实时预览共用一套渲染。`dsh-plugin/src/workbench-view.ts` 本来就是纯函数（`createElement` 作参数传入），网页端直接传 `React.createElement` 就能复用。做到同一份配置、同一套代码、两边长得一样。布局按手机宽度做适配，**手机上能用**是网页版最大的价值之一。

**取数**：新增 `POST /api/me/apps/{slug}/source`，按员工的网页会话确定身份，走现有连接网关的只读工具、知识库工具和 `app` 工具，权限、额度、审计都和 DSH 里一样。

**网页上没有 AI，那些地方怎么办**：

| 组件 / 操作 | 网页上的行为 |
|---|---|
| 指标、表格、图表、清单、详情卡、标题、说明 | 照常显示 |
| 表单提交到自带的表 | 直接提交 |
| 表格编辑自带的表（按可见性） | 直接编辑 |
| 快捷按钮、行按钮、提交给 AI 的表单（发话给 AI） | 显示为「在 DSH 里继续 ↗」，用深链接打开 DSH，把这段话带过去；没装 DSH 的人看到的是置灰的说明 |
| AI 看板 | 显示最近一次的内容（只读），或者隐藏 |

这样，同一个应用对**不装 DSH 的人**（管理层、外勤、手机用户）也有用。这些人往往正是数据的提供者或查看者，比如报名的人和看报名结果的人。

### 10.5 数据中台：小，而且只做两件事

前面讨论过的数据中台，定位是「唯一数据源」，范围收得很小：

1. **放数据进来**：网页上上传 CSV / Excel，生成一张表，之后可以覆盖或追加；也可以由管理员写 SQL 建表、导入。**不做定时同步和 ETL**，要同步企业系统，交给社区写连接，或者企业自己的脚本往库里写。
2. **把数据用出去**：管理员定义**数据集**，也就是一条带名字、带说明、可带参数的只读查询，比如「客户主数据」「近 12 个月 GMV」。数据集挂在系统连接 `data` 下：
   - 工作台和应用自带表的 `ref` 只能用数据集，结果稳定、口径统一；
   - AI 另外可以用 `data__tables`、`data__describe`、`data__query`（只读 SQL，限行数、限时长）做探索式分析，并且只能在员工有权限的表里查。

**存储**：沿用 dsh-ee 已经依赖的 MySQL 兼容库（TiDB / MySQL / OceanBase），单独建 `dsh_ee_data` 库，用一个**只有查询权限**的数据库账号来执行查询。只读由数据库保证，不靠我们自己解析 SQL；TiDB 上用 `MAX_EXECUTION_TIME` 限时。暂不引入 DuckDB：它的 Go 驱动需要 cgo，会破坏现在 `CGO_ENABLED=0` 的单文件静态编译和离线安装包。以后如果需要分析本地的 CSV / Parquet，再作为可选插件考虑。

**权限**：数据集和表的可见范围沿用连接的「部门 / 角色 / 个人」。行级权限第一版不做；需要按部门分的数据，就用带参数的数据集，参数由服务端自动填成员工所在的部门，员工改不了。

**从应用长成企业数据（升格）**：一个应用的自带表用的人多了，或者别的应用也想用它，作者可以申请「升格到中台」。管理员审批后，这张表变成中台里的真实表和一个数据集，原应用自动改为引用它。这是 §4 飞轮在数据上的版本：**员工先在自己的小应用里把数据攒起来，好用的再变成全公司的唯一数据源**。和 `/ee-save` 把对话沉淀成能力是同一个思路。

### 10.6 单点登录：从 DSH 打开网页不再登录

**原因**：DSH 里用的是设备令牌，网页认的是会话 cookie，两者不相通。插件里的「看原文」「申请权限」「应用详情」都是直接打开网页，Desktop 里很可能是在内置浏览器标签页里打开的，它和系统浏览器不共享 cookie（待在 Mac 上确认）。

**做法**：插件带设备令牌请求 `POST /api/me/web-link {next}`，服务器返回一次性的 `…/api/auth/handoff?code=…`（只能用一次，60 秒有效）。打开这个链接时，服务器发会话 cookie，然后跳到目标页。插件里所有指向 dsh-ee 网页的链接都改走这一步；网页版应用的「从 DSH 打开」也走这一步。

**三条安全底线**：
- 这样换来的网页会话**不带管理权限**，管理模式照旧要输密码、并且限时；
- code 用过一次即作废，跳转后地址里不留 code，免得经 Referer 或浏览器历史泄露；
- 浏览器里已经登录着**别人的账号**时**不替换会话**：回到登录页提示「当前浏览器已登录其他账号，请先退出当前账号，再从 DSH 重新打开链接」，也不自动登出（否则任何人发一条链接就能把同事踢下线）。没有会话、或已登录的是同一个人，保持原有行为。

**打开企业的其他系统也免登录**：这件事靠企业自己的身份系统。dsh-ee 已经支持 OIDC（M10），企业的其他系统接同一个 IdP，浏览器里登录一次就都通了。**dsh-ee 不做身份提供方（IdP）**：安全责任大、维护重，不适合个人维护的开源项目。

### 10.7 在 DSH 里用 AI 造应用

有了自带数据，「造应用」最自然的入口就是对话：员工在 DSH 里说「帮我做一个下周团建报名的小应用，要收集姓名、场次和忌口」，AI 就生成一个「自己用」的应用草稿，包括表结构、工作台（报名表单 + 报名列表 + 按场次统计的饼图）和示例问题，并且立刻能打开试用。

实现上，给员工侧加一个 `ee_app` 工具，只能新建和修改**自己的「自己用」应用**；分享仍然要在网页上改范围、走审核。（实现时改为给现有的 `ee_hub.create` 加 `for_me` 参数，效果相同，见任务清单 M13 的完成情况。）它和 M9 的 `/ee-save` 可以共用一套「草稿 → 自己用 → 分享」的流程。这一项会是演示视频里最有冲击力的一段：**一句话做出一个能在手机上填的小系统。**

### 10.8 对样板与示例公司的影响

- 第一批样板里，「新人入职助手」的入职清单可以改成自带表（`own` 模式），HR 在网页上能看到所有新人的进度；
- 在星河科技里加一个「自带数据」的样板，比如**团建报名**或**设备借用登记**，演示网页版、手机填写和 AI 统计（已做：吴敏的「团建报名」，报名各自填写、公告作者发布）；
- 中台预置「客户主数据」「组织与人员」两个数据集，从演示 CRM 导入，客户拜访简报改为引用数据集；
- 一键清除时，自带表的行和中台的示例表一起清掉（沿用 `demo_records`）。

## 11. 宣传亮点与设计理念（2026-11-08）

> 用途：README 首屏、落地页、发布文章和演示视频都从这里取材。§5.1 的三个关键词仍然有效，这一节是有了 §10 以后的展开版。

### 11.1 五个亮点（按宣传优先级）

**① 一个应用，两个入口，三层数据**（最强的差异化）

- 两个入口：同一个应用在 DSH 里有 AI（对话、改数据、审批卡），在网页 `/a/<应用标识>` 上手机也能看、能填；两边是同一份配置、同一套渲染。网页上要 AI 时，「在 DSH 里继续」。
- 三层数据：应用自带的小表、中台的唯一数据源（数据集）、企业现有系统（连接）。主数据只有一份，应用里存编号不存副本。
- 来回免登录：从 DSH 打开网页走一次性登录链接。
- 一句话：「**员工在 DSH 里让 AI 帮着做，同事在手机网页上直接用，数据都是公司的那一份。**」
- 措辞注意：dsh-ee 是私有部署，宣传里说「网页端」「企业服务端」，不说「云上」，免得安全负责人误以为数据要上公有云。

**② 人人都能搭建，而且放开也安全**

- 「自己用」免审核，改范围才进审核；在 DSH 里一句话就能做出一个手机上能填的小系统（如「团建报名」）。
- 能放开的原因：**应用本身不带权限**。应用只能用作者本人已有权限的原料，运行时用的是使用者本人的身份，员工做的应用做不到他本人做不到的事。这句话直接回答 IT 最怕的「员工乱建」。

**③ AI 能办事，每一步都可信**

- 企业系统的写操作一律「AI + 审批卡」；面板直接写只限应用自带的表。
- 知识库不用向量：Agent 多轮检索、读原文，回答带出处和行号。
- 凭据不落员工电脑，全部走连接网关，每次调用有记录。
- 和聊天机器人、传统低代码的区别：**能办事，而且办的每件事看得见、查得到。**

**④ 企业级底座全部开源，一个文件就能部署**

- RBAC、LDAP / OIDC、按人额度、模型网关与故障转移、npm 源审核、审计、离线安装包、单文件静态二进制、月度 AI 落地报告。
- Apache-2.0，不分版本。放在第二屏，作用是消除顾虑，不负责吸引注意；真正能讲的差别是「全部开源」和「离线单文件」，不是「企业级」三个字。

**⑤ 十分钟见效**

- 示例公司「星河科技」一键导入（实测 3～4 秒）、一键清除且不动自己的内容；4 个样板应用、仿真的 CRM / 工单 / 差旅、30 天曲线。

### 11.2 设计理念

1. **应用是唯一的主角。** 员工想的是「我要报销」，原料只在「造」的时候出现。
2. **权限在原料上，不在应用上。** 所以搭建可以放开，安全由一个网关、一套授权兜底。
3. **一份数据说了算。** 主数据只在中台或企业系统；员工先在小应用里攒数据，好用的再升格。
4. **复用，不新增。** 同一份配置、同一套渲染、同一个网关、同一套审计；不新增资产类型。
5. **不和现有系统抢地盘。** 不做门户、不做工作流编排、不做 IdP；只做「把企业的知识和数据变成员工手里的 AI 应用」。
6. **飞轮：** 用 → 反馈 → 沉淀 → 复用（👍👎 与答不上来的问题、`/ee-save`、数据升格）。

### 11.3 对谁怎么讲

| 对象 | 顾虑 | 讲哪几条 |
|---|---|---|
| IT / 数字化负责人（主要目标用户） | 推不动、没法向上汇报 | ⑤、②，加月度落地报告：「一周让 200 人用起来，还有数据给老板看」 |
| 安全 / 法务 | 数据外泄、乱装、AI 乱动系统 | ③、④：私有部署、凭据不落地、审批卡、审计、应用不带权限 |
| 业务部门员工 | 和我有什么关系、难不难学 | ①、②：十分钟做个自己的小系统，手机上也能填 |
| 老板 | 花多少钱、见不见效 | 开源免费、按人额度防失控、落地报告里的活跃率和节省工时 |

常见质疑「这不就是共享表格加聊天机器人？」的回答：它天然带公司身份和权限，AI 能读企业系统、经审批能办事，而且数据只认一个源头。
