## 0. 结论

1. **功能已经够发布了，缺的是收口。** M1～M15 除 M9、M11 外都已完成，离 v0.1 差的是：修掉遗留的失败测试、补完真机验证、把知识库打磨到能当招牌、写发布材料。
2. **v0.1 前冻结范围（已定）。** 第一个公开版本叫 v0.1，对应 product-v1 系列文档里说的「第一版 / v1.0」。8 条 todo 里只有第 1、3 条和第 8 条的一部分属于「发布前」；飞书、多 Agent、插件系统、OCR / 向量都放到 v0.1 之后。原因见 §3。
3. **v0.1 之后的顺序：飞书（v0.2）→ 插件系统与多 Agent（v0.3）→ 知识库再完善（v0.4）→ 企业级运行能力（贯穿各版）。** 这和最初列的顺序不完全一样，理由在各节里。
4. **5 个方向性问题已在 2026-11-10 定下**，记在 §6：dsh-ee 暂不自己跑 AI；插件系统指 dsh-ee 自身的插件；目标是「办事的第一入口」；v0.1 前冻结范围；其他 Agent 先留接口。

## 1. 理念

落地页和 README 讲的是同一件事：

> AI 工具不缺，缺的是把企业**自己的**知识和系统，安全地送到每位员工手里。

展开成 6 条设计理念（product-v1.md §11.2），后面的路线都用它们来判断该不该做：

| # | 理念 | 路线里用它判断什么 |
|---|---|---|
| 1 | 应用是唯一的主角 | 新功能要落到「员工在应用里得到什么」，不新增资产类型 |
| 2 | 权限在原料上，不在应用上 | 新入口（飞书、其他 Agent）必须走同一个网关、同一套授权 |
| 3 | 一份数据说了算 | 不为新入口另存一份数据 |
| 4 | 复用，不新增 | 同一份应用配置、同一套渲染、同一套审计 |
| 5 | 不和现有系统抢地盘 | 不做门户、不做工作流编排、不做 IdP |
| 6 | 飞轮：用 → 反馈 → 沉淀 → 复用 | 优先补闭环上的断点（如 `/ee-save`） |

另有一条写在 README 里的架构前提：**dsh-ee 本身不跑 AI，推理与工具调用都在员工本机的 DSH 里。** 第 4、5、6 条 todo 都会碰到它（§6 问题 1）。

落地页与实际能力的差距：落地页主打的仍是「能力中心、审核、接入、模型网关」这套底座；product-v1.md §11 定的五个亮点（一个应用两个入口三层数据、人人都能搭建、十分钟见效）还没体现在落地页上。这是 v0.1 发布材料要补的。

## 3. 为什么要先发布，再做飞书和多 Agent

之前定的是「先把全部功能做完再发布」。当时的「全部功能」指 M1～M15，现在已经做完。新的 todo 里第 2、4、5、7 条每一条都是一个版本的工作量，如果都排在发布前：

- 发布会无限后移，而 product-v1.md §5.3 的「三个陌生人十分钟测试」、§6.4 的公开信号一直拿不到，后面这些大功能就只能凭猜测排优先级；
- 上游 DSH 还在 rc 阶段，未发布的代码每多一块，跟上游的维护量就多一块；
- 飞书和多 Agent 的细节值得先听真实用户的需求再定。

已定（2026-11-10）：v0.1 前冻结范围。

## 4. 路线

### 阶段 A：收口

目标：主分支全绿，已做的功能都验证过。

1. 修遗留的 Go 测试失败，让 `make test` 全过。
2. 消除 e2e 的顺序依赖：每个测试自己准备数据，全量跑和单跑结果一致。
3. 修 M9 `/ee-save` 的提炼消息投递。
4. 清真机验证欠账（§2.2 那一行），结果写回各 verify 文档。Desktop 上验证 logo 修复（todo 3 的收尾）。
5. 上游兼容：以 DSH 0.2.2 正式版为基准重跑全部真实 DSH 场景，起草兼容性矩阵。

完成标准：CI 全绿；各 verify 文档里没有「待补」；M9 状态改成已验证。

### 阶段 B：知识库完善（todo 1）

目标：知识问答是员工最先用到的功能，要做到能当招牌。P1～P4 已实现，这一阶段是验证和补洞，不是重做。

| 方向 | 要做的 |
|---|---|
| 检索 | 建一份评测集（星河科技的文档 + 50～100 个带标准出处的问题，含条款号、同义说法、跨文档、表格、没有答案这几类），用真实模型跑，记录命中率、检索轮数、token 用量。它既是回归测试，也是阶段 F 判断要不要加向量的依据 |
| 阅读 | 出处跳转、行高亮、长文档目录、表格与 PPT 的阅读视图在 Desktop 和手机网页上都走一遍；版本对比（新版本改了哪几段） |
| 引导 | 空库时的第一步引导、上传后的体检结果怎么读、「试搜」怎么判断好坏、「待补文档」到「补一篇文档」的闭环；员工侧答不上来时给出下一步（去哪问、提交待补） |

完成标准：评测集进 CI（假模型跑流程）并有一条手动的真实模型跑法；knowledge-verify.md 全部通过。

### 阶段 C：发布 v0.1（M11 + todo 8 的发布部分）

1. **发布材料**：README 与落地页按 product-v1.md §11 的五个亮点重写；截图、动图；快速开始、员工指南、管理员指南、部署与升级四份文档；兼容性矩阵。
2. **发布工程**：版本号与变更记录；GitHub Release 自动产出两种架构的离线包、镜像与校验和；升级说明（迁移只增不改、主密钥保留）；一次真实的旧版本升级演练。
3. **运行底线**：备份与恢复说明并演练一次（数据库 + 数据目录 + `.env`）；健康检查接口；日志说明；安全自查（令牌、一次性登录链接、网页版应用的权限、上传解析的资源上限）与 SECURITY.md。
4. **社区入口**：CONTRIBUTING、Issue 模板、「谁在用」帖、应用模板仓库。
5. **三个陌生人十分钟测试**，卡在哪改哪。
6. 最后录演示视频。

完成标准：三个人只凭 GitHub 链接都能在自己电脑上走通。

### 阶段 D：v0.2 飞书接入（todo 5）

排在多 Agent 之前，因为国内企业的组织、通知、审批都在 IM 里，这是真实部署最先会被问到的。分两步，第一步不需要 dsh-ee 跑 AI：

| 步骤 | 内容 | 是否要 dsh-ee 跑 AI |
|---|---|---|
| D1 | 飞书扫码 / 免登登录（走 OIDC 或飞书 OAuth）；同步部门与人员到可用范围；通知（审核结果、权限申请、额度告警、待补文档）；审核与权限申请的卡片内直接通过 / 驳回；飞书工作台里打开网页版应用（免登录） | 否 |
| D2 | 飞书机器人问答：在飞书里问知识库、用应用 | **是**，见 §6 第 1 条 |

v0.2 只做 D1。做的时候把「登录来源、组织同步、通知渠道」写成三个内部接口，钉钉、企业微信之后照着接，可以交给社区。D2 不在 v0.2 里，等 v0.3 之后验证服务端最小循环时再看。

> 分批实现进度：[feishu.md](./feishu.md) 已覆盖 D1 的飞书免登登录、部门/人员同步、目录失效禁用、审核结果/权限申请卡片、工作台入口，以及 npm CLI 与网页上传的插件审核卡。额度告警、预载等批量场景通知和机器人问答仍未实现，不能把 D1 整体标为完成。

插件第一批已补 [多份命名共享凭据](./named-shared-credentials.md)：连接能保存生产、测试等多份共享凭据并选择实际使用的一份，旧默认凭据兼容；按应用分别绑定和声明式扩展的 `validate` 仍待下一批。

### 阶段 E：v0.3 插件系统与多 Agent（todo 2、todo 4）

> **2026-11-11 补充：** 这一阶段已经细化成三份设计稿，以它们为准：
>
> - [plugins.md](./plugins.md)：dsh-ee 自身的插件改叫「扩展」（「插件」在产品里已经指 DSH 插件）。三种形式：声明式（清单 + OpenAPI，不写代码）、服务（企业自己部署，Go SDK）、内置（飞书等）。服务端不运行第三方代码。凭据按员工本人的身份。
> - [access-control.md](./access-control.md)：可关闭的超级管理员、互斥角色；文档和用户的扩展字段，按字段控制谁能看。
> - [agent-dev.md](./agent-dev.md)：配套技能、规格和测试工具，让 Agent 完成扩展和权限配置的开发。
>
> 工作分成五批，每一批单独能发布，顺序见 [plugins.md](./plugins.md) §12。其中**第 1 批（按人身份 + 声明式扩展）提前到 v0.2**，和阶段 D 的飞书并行；下面表里的各类插件对应到扩展点的关系见 [plugins.md](./plugins.md) §14.4。

这两条放在一起，因为是同一件事的两面：把 dsh-ee 与 DSH 的耦合收到一个边界后面，再把边界做成插件接口。支持 Codex、Claude Code、OpenCode 这类 Agent，和自定义权限管理，都是这套插件系统上的插件。

**现状：** 服务端面向 Agent 的部分大多已经是标准协议：`/v1` 是 OpenAI 兼容，`/mcp` 上有企业连接、`kb__`、`app__` 和 `ee_*` 工具。DSH 专属的是：接入插件（界面槽位、工作台渲染、`/ee-*` 命令、审批卡）、插件索引 `/index/dsh-index.json`、接入脚本写的配置、Desktop 分发、品牌接管。

**todo 4 支持其他 Agent，分三级：**

| 级别 | 其他 Agent 能得到什么 | 工作量 |
|---|---|---|
| L1 协议级 | 用统一令牌接模型网关和 `/mcp`：企业连接、知识库检索、应用数据。没有工作台界面 | 小：接入页按 Agent 生成配置片段，文档化工具清单，补一组「非 DSH 客户端」的测试 |
| L2 应用级 | 应用（人设 + 技能 + 提示词 + 示例问题）以该 Agent 的原生形式下发，如技能目录、斜杠命令 | 中：把「目录 → 客户端形式」做成适配器接口，DSH 是第一个实现 |
| L3 界面级 | 工作台面板 | 大：取决于对方有没有界面扩展能力；没有就用网页版应用兜底 |

已定（2026-11-10）：留接口就行，不指定先支持谁，Claude Code、OpenCode、Codex 都可以。所以 v0.3 做 L1（对所有支持 MCP 和 OpenAI 兼容接口的 Agent 通用），L2 只定适配器接口并把 DSH 改成它的第一个实现，其他 Agent 的适配器作为插件由需要的人来写。写操作的审批卡在 L1 下没有客户端界面，需要一个服务端兜底（网页或飞书卡片上确认），这是 L1 的主要安全工作。

**todo 2 插件系统：** 已定（2026-11-10）：指 dsh-ee 自身的插件，让别人不改主仓库就能加东西，例如支持 Codex / Claude Code、自定义权限管理。约束是单文件和 `CGO_ENABLED=0`，所以不做进程内加载，插件是一个独立进程或服务，dsh-ee 通过协议调它：

| 插件类型 | 形式 | 现状 |
|---|---|---|
| Agent 适配器 | L2 的接口：把应用目录转成某个 Agent 的原生形式，并生成该 Agent 的接入配置 | 新增；DSH 是内置实现 |
| 权限策略 | 授权决策钩子：在现有 RBAC 判定之后，把「谁、对什么、做什么」发给外部策略服务，由它允许或拒绝 | 新增；内置实现就是现有 RBAC |
| 登录与组织同步 | 阶段 D 抽出的接口 | 新增；飞书是内置实现 |
| 通知渠道与事件 | Webhook（发布、审核、申请、反馈、额度），带签名与重试 | 新增；飞书通知是内置实现 |
| 文档解析 / OCR | 外部 HTTP 转换服务 | 新增，阶段 F 用 |
| 业务系统 | MCP 服务 / OpenAPI 文档 | 已有 |
| 应用模板 | 导出文件 + 模板仓库 | 已有导入导出，仓库在阶段 C |

要做的还有：插件的注册与启停页面、健康检查、调用审计、协议版本号。每种插件类型都要有一个内置实现和一份协议文档，否则不算完成。

权限策略插件有两条底线：只能在内置 RBAC 允许的基础上再收紧，不能放宽；策略服务连不上时一律拒绝。这样装错或写错一个插件不会造成越权。

### 阶段 F：v0.4 知识库再完善（todo 7）

| 项 | 建议 |
|---|---|
| OCR | 做，但不进主程序：扫描页交给外部服务（一个 OCR HTTP 接口，或经自己的模型网关调视觉模型），没配置时保持现在的「扫描页占位不收」。需要后台入库任务与进度，这是当初没做的主要原因（knowledge-next.md §9） |
| 向量 | 先不决定。用阶段 B 的评测集和 v0.1 之后「答不上来的问题」数据来判断：如果失败集中在同义改写，先试查询改写和同义词表；仍然不够，再把向量做成**可选**的补充召回（外部 embedding 接口 + TiDB / OceanBase 自带的向量类型），不配置时行为不变，出处与行号核对照旧 |
| 其他 | 图片与图表里的文字、大库的检索速度、跨库权限下的统一搜索，按评测结果排 |

「不依赖向量模型」是落地页上的卖点，改成可选项时宣传口径要跟着改成「不需要向量模型也能用」。

### 贯穿各版：企业级运行能力（todo 8 的其余部分）

不单独成版，按真实部署反馈插进各版本：

- **多实例**：限流、缓存、预载任务移出进程内存（用数据库），tarball 支持对象存储。这是「已知限制」里最硬的一条，建议不晚于 v0.3。
- **身份**：SCIM 或 IM 组织同步（阶段 D 带一部分）、离职自动吊销令牌。
- **审计与合规**：审计日志导出与外发（syslog / Webhook）、保留期设置、操作留痕覆盖所有管理动作。
- **可观测**：指标接口、慢请求日志、上游模型的延迟与错误率。
- **运营**：月度报告继续打磨，应用作者能看到自己应用的使用与反馈。
- **升级**：每个版本都有升级说明和回滚说明，CI 里跑上一个版本到当前版本的升级测试。

### 远期：Agent 作为办事的第一入口（todo 6）

已定（2026-11-10）：目标不是「唯一入口」，是「办事的第一入口」。员工想办一件事时先想到问 Agent，Agent 去调各个系统；飞书里也能触达同一批应用。不做门户，不替代飞书和 OA。

它不单独成版，靠前面各阶段累积：首屏启动台与工作台系统应用（已有）、飞书里打开应用（v0.2）、更多 Agent 能接入（v0.3）、连接器和样板应用变多（社区）。衡量办法是月度报告里「经 Agent 办成的事」的数量和覆盖的系统数。

## 6. 已定的决定（2026-11-10）

1. **dsh-ee 暂不自己跑 AI。** v0.2 保持不跑，飞书只做登录、组织、通知、审批，问答引导回 DSH。v0.3 的协议级接入做完后，再用一个最小的服务端循环验证（只用 `/mcp` 上的只读工具，写操作转成确认卡片），范围先只限知识问答。不在服务端跑无界面的 DSH。
2. **插件系统指 dsh-ee 自身的插件**，例如支持 Codex / Claude Code、自定义权限管理（阶段 E）。
3. **目标是「办事的第一入口」，不是「唯一入口」。**
4. **v0.1 前冻结范围**；第一个公开版本叫 v0.1。
5. **其他 Agent 留接口就行**，不指定先支持谁，Claude Code、OpenCode 等都可以。

## 7. 风险

| 风险 | 应对 |
|---|---|
| 范围继续扩大，发布后移 | §3 的冻结；每个阶段有完成标准，没达到不开下一个 |
| 上游 DSH 变动 | 兼容性矩阵；真实 DSH 场景进 CI；多 Agent 的协议级接入本身也是对冲 |
| 多入口后权限不一致 | 所有入口走同一个网关和同一套授权（理念 2）；每加一个入口补一组越权测试 |
| 引入 OCR / 向量 / 服务端 Agent 后部署变重 | 一律做成可选、进程外、不配置时行为不变 |
| 一个人维护 | 扩展点都配协议文档，钉钉 / 企业微信、连接器、模板、第二个 Agent 适配器交给社区 |
